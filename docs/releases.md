# 版本与发布

页隐采用 [SemVer](https://semver.org/lang/zh-CN/) 管理版本。兼容的修复增加修订号，兼容的新功能增加次版本号，影响安装、数据或公开接口兼容性的重大变更增加主版本号并提供迁移说明。

`alpha.N` 用于早期验证，`beta.N` 用于功能基本完成后的测试，`rc.N` 用于发布候选。每个阶段的序号从 1 开始，同阶段依次增加。正式版使用三段版本号，例如 `2.0.0`。Git 标签加小写 `v`，例如 `v2.0.0-rc.1`。预发布标记为 prerelease。历史 debug 构建保留在[变更日志](../CHANGELOG.md)中。

`develop` 是集成分支。稳定版来自 `main` 已验收的提交。稳定版热修复以受影响的稳定源码为基线，发布修订版后再同步到 `develop`。

## 发布检查

1. 定义发布范围，把已验证的用户可见变化归档到[变更日志](../CHANGELOG.md)，补充适用平台和升级步骤。
2. 在源码中设置版本，使 `package.json`、锁文件、应用和后端使用同一版本。发布流程检查标签与源码是否一致，版本不一致时终止。
3. 完成[回归测试](public/testing.md)，用当前源码在 macOS 和 Windows 分别构建原生包。涉及安装或数据迁移时，分别验证旧版升级、凭据读取和卸载。
4. 核对 AGPLv3 项目许可证、对应源码和每个平台实际分发组件的许可及声明。草稿同时附上校验过的 PyMuPDF、MuPDF、CPython 和发行 Python 所用 OpenSSL 的源码。根据该次实际构建补齐其他组件的许可声明及适用源码，再批准发布。发行包使用普通构建，测试包单独用于自动化。
5. 两端安装包、标签对应的项目源码归档、`SHA256SUMS.txt`、源码提交和发布说明汇集到同一个 GitHub Release 草稿。维护者核对平台、已知限制、升级注意事项和验证范围后批准发布。
6. 从 Release 重新下载附件，核对 SHA256、实际打开和显示版本。按此次变更范围复查处理、升级和更新检查。

Windows Setup 只携带一个完整包，保留旧版安装标识。打包时用更新器实际使用的 NuGet 读取器打开完整包清单。Windows 发行门禁核对实际 Setup 的启动器代码、完整包的原始 ZIP 条目和包字节、两份更新器及随包的安装器许可。启动器和更新器的构建脚本、上游源码锁和补丁包含在项目源码归档中。

`develop` 上的版本和构建配置变更会构建两端候选并上传到该次 CI 的产物。版本标签触发双端验证。验证通过后，默认由工作流准备 GitHub Release 草稿。采用已验收的本地发行附件时，维护者在推送版本标签前设置 `REDACTERA_RELEASE_ASSET_SOURCE=local`，再用同一套已验收附件准备草稿。

公开发行从 Redactera 2.0.0 开始。2.0.0 及后续版本通过 [WaterGauge/redactera 的公开 Releases](https://github.com/WaterGauge/redactera/releases) 检查更新和下载。测试者可使用获授权的账号下载私有验证产物。

1.x 用户请从同一 Releases 页面下载 2.0.0 的 DMG 或 Setup.exe，核对 SHA256 后手动安装。Windows 使用覆盖升级流程。macOS 从旧名应用升级时按 [安装指南](handbook/mac-signing-notarization.md#从旧名版本升级)操作。

发布过的标签和安装包对应同一组字节。修复发布问题使用新的修订版或候选号。需要回退时说明已验证的目标版本与设置兼容性。涉及敏感信息残留时，发布说明应写明过去的输出是否需要复查或重新处理。
